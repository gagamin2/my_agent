# Code Analysis Skill

## 作用

用于分析项目中的代码、文件、模块和功能，
帮助 Agent 理解代码结构、执行流程、模块关系以及潜在问题。

## 使用场景

当用户要求 Agent：

- 分析代码
- 解释文件作用
- 理解项目结构
- 分析某个模块
- 分析某个功能的实现
- 查找某个功能对应的代码
- 理解多个文件之间的关系
- 定位代码问题

时，可以使用这个 Skill。

## 执行步骤

### 1. 理解任务

首先明确用户希望分析的对象和目标。

判断当前任务属于：

- 单个文件分析
- 多个文件分析
- 模块分析
- 功能分析
- 项目结构分析
- 问题定位

不要在没有明确目标的情况下读取大量文件。

### 2. 了解项目结构

如果当前不了解项目结构：

使用 `list_files` 查看相关目录。

不要在不了解项目结构的情况下随意猜测文件路径。

### 3. 定位相关代码

如果需要查找某个功能或代码：

使用 `search_files` 搜索相关关键词。

例如：

- 函数名称
- 类名称
- 变量名称
- 模块名称
- 功能名称

根据搜索结果确定需要进一步读取的文件。

### 4. 读取关键文件

使用 `read_file` 读取与任务直接相关的文件。

只读取完成当前任务所需要的文件。

如果已经获得足够的信息，不要继续读取无关文件。

### 5. 分析代码

重点分析：

- 文件的主要作用
- 核心函数和变量
- 模块之间的关系
- 数据从哪里进入
- 数据经过哪些处理
- 最终结果在哪里产生
- 重要的调用关系
- 关键执行流程

分析必须基于实际读取到的代码。

### 6. 必要时进行验证

如果用户的问题涉及：

- 项目能否构建
- TypeScript 是否存在错误
- 测试是否通过
- 某个命令是否能够执行
- 某个功能是否能够运行

可以使用 `run_command` 进行验证。

只有在确实需要验证时才执行命令。

不要为了分析代码而执行没有必要的命令。

### 7. 形成结论

完成分析后，停止继续调用工具并整理最终结果。

最终结果应该明确回答用户的问题。

### 8. 核对分析结果

在输出最终结论之前：

- 检查结论是否能够从已经读取的代码中得到支持。
- 检查是否把函数名称、工具名称或推测当成了实际实现。
- 对具体问题重新核对对应源码。
- 删除没有代码依据的结论。
- 如果存在不确定内容，应明确标记为推测，而不是事实。

## 工具使用原则

根据任务选择合适的工具。

推荐的基本流程：

`list_files` → `search_files` → `read_file`

如果已经知道目标文件，可以直接使用：

`read_file`

如果需要验证代码或项目状态，可以在必要时使用：

`run_command`。

不要机械地执行所有工具。

## 注意事项

- 不要修改原文件。
- 不要删除文件。
- 不要在没有读取文件的情况下猜测代码内容。
- 不要假设项目中存在没有确认过的文件。
- 如果文件不存在，应明确告诉用户。
- 不要无目的地读取大量文件。
- 不要重复读取已经获得足够信息的文件。
- 不要重复执行相同命令。
- 如果已经获得足够的信息，应停止工具调用。
- 如果信息不足，应继续寻找必要的信息。
- 如果仍然无法确定，应明确说明无法确定的部分。

## 分析原则

代码分析必须以实际代码为依据。

对于代码中明确存在的内容，可以直接进行分析。

对于无法从当前代码确认的内容，不应该猜测。

如果需要多个文件才能确定问题，应继续查找相关文件。

分析过程中应优先关注与用户问题直接相关的代码。

### 代码事实核对

当分析具体代码行为时：

- 必须以实际读取到的源码为依据。
- 不要根据工具名称、函数名称或过去的上下文推测实现。
- 如果需要判断某个函数的返回值，应读取该函数的实际实现。
- 如果需要判断模块之间的调用关系，应读取相关调用方和被调用方。
- 如果发现潜在问题，应明确指出问题对应的代码依据。
- 不要因为某个模块“看起来应该这样工作”就认为它实际就是这样工作的。

如果无法从当前读取到的代码确认某个结论：

- 继续读取必要的代码；
- 如果仍然无法确认，应明确说明“无法从当前代码确认”；
- 不要自行补全不存在的实现。

## 输出要求

最终输出应该包含：

1. 分析结论
2. 关键文件
3. 核心结构
4. 主要函数和模块
5. 重要执行流程
6. 文件或模块之间的关系
7. 发现的问题（如果存在）
8. 原因分析（如果存在）
9. 建议（如果需要）
