# Community Skill Recommendation

当 Agent 获取到 SkillHub 社区 Skill 后，需要根据当前工具返回的数据，对 Skill 进行分析，并筛选出值得用户关注的 Skill。

## 一、分析目标

不要简单复述 Skill 列表。

需要结合 Skill 当前返回的：

- name
- description
- description_zh
- category
- tags
- downloads
- stars
- installs
- score
- labels

等信息，判断 Skill 的实际价值，并给出推荐等级。

如果工具返回的信息不足以判断某个维度，应明确说明“信息不足”，不要自行推测。

---

## 二、分析维度

### 1. 实用性

判断 Skill 是否能够解决实际问题，以及是否具有明确的使用价值。

等级：

- 高
- 中
- 低

重点关注：

- 是否存在明确的使用场景
- 是否能够解决实际问题
- 功能是否具有实际价值

### 2. 通用性

判断 Skill 是否能够应用于多个项目或多个场景。

等级：

- 高
- 中
- 低

如果 Skill 只针对非常具体的场景，则通用性可以评为“低”。

### 3. 社区热度

可以参考当前工具返回的：

- downloads
- stars
- installs
- score

等级：

- 高
- 中
- 低
- 信息不足

不能仅根据单个数字判断推荐等级。

如果缺少足够的社区数据，应使用“信息不足”。

### 4. 新颖性

根据 Skill 的名称、描述、分类和标签，判断其是否提供了比较新的能力、工作流或解决方案。

等级：

- 高
- 中
- 低
- 信息不足

如果当前数据无法判断，应使用“信息不足”。

### 5. 安全性

根据当前工具返回的 Skill 信息，判断是否存在明显的安全风险。

等级：

- 高
- 中
- 低
- 信息不足

重点关注 Skill 是否涉及：

- 执行代码
- 执行 Shell 命令
- 文件系统访问
- 网络请求
- 安装依赖
- 修改系统
- 访问敏感数据

如果当前数据无法确认是否存在相关风险，应使用“信息不足”，不要自行推测。

如果发现明显安全风险，不应该给出“⭐ 强烈推荐”。

---

## 三、推荐等级

综合以上分析维度，为每个 Skill 给出一个最终推荐等级。

### ⭐ 强烈推荐

通常满足以下多个条件：

- 实用性高
- 通用性较强
- 有明确的使用场景
- 有一定社区认可度
- 没有当前数据能够确认的明显安全风险

### 🟡 可以关注

Skill 具有一定价值，但存在以下情况之一：

- 使用场景比较有限
- 社区数据较少
- 功能比较普通
- 某些分析维度信息不足
- 存在一定限制，但仍具有关注价值

### ⚪ 暂不推荐

存在以下情况之一：

- 实际价值较低
- 使用场景非常有限
- 描述不清晰
- 功能与常见 Skill 高度重复
- 当前数据能够确认存在明显安全风险

推荐等级必须综合多个分析维度判断。

不能仅仅因为 downloads、stars、installs 或 score 较高，就直接判定为“⭐ 强烈推荐”。

---

## 四、数据与事实约束

### 1. 数据来源

本次推荐只能基于 `get_community_skills` 当前调用返回的数据。

如果工具返回空列表，表示当前没有发现新的 Skill。

此时不要重新推荐历史消息中的 Skill，也不要把以前见过的 Skill 当作新的 Skill。

### 2. 禁止编造信息

不要补充工具结果中不存在的事实。

对于以下信息尤其需要谨慎：

- 作者
- 认证状态
- API Key
- 开源状态
- 具体功能
- 安全风险
- 使用方式
- 技术实现

如果当前工具数据无法确认，应明确说明：

> 信息不足

不要根据 Skill 名称、常识或其他历史信息自行推测。

### 3. 分页规则

如果工具返回了分页信息，只能将其理解为当前分页结果。

不要因为当前结果来自某个分页，就声称这些 Skill 是：

- 最新
- 最热门
- 最受欢迎
- 全部 Skill

除非当前工具返回的数据能够直接支持这些结论。

### 4. 推荐依据

推荐理由必须能够从当前工具返回的 Skill 数据中找到依据。

不要为了让推荐理由看起来完整而添加工具结果中不存在的信息。

---

简要说明为什么给出当前推荐等级，并使用当前 Skill 数据中的实际信息作为依据。

**适合场景：**

说明根据当前 Skill 信息可以确认的适用场景。

**风险：**

说明当前数据能够确认的明显风险。

如果无法判断，写：

> 信息不足

---

**评分：**

- **安全性：** 0～10 / 信息不足
- **总分：** 0～50

**推荐理由：**

简要说明为什么值得关注，以及当前存在的限制。

**风险：**

如果无法判断，写：

> 信息不足

---

## 六、评分规则

五个维度分别使用 0～10 分进行评分：

- 实用性
- 通用性
- 社区热度
- 新颖性
- 安全性

五个维度相加得到总分：

实用性 + 通用性 + 社区热度 + 新颖性 + 安全性 = 总分

满分为 50 分。

推荐等级参考：

- 41～50：⭐ 强烈推荐
- 26～40：🟡 可以关注
- 0～25：⚪ 暂不推荐

### 安全兜底规则

如果当前数据能够确认 Skill 存在明显或严重的安全风险：

- 不得给出“⭐ 强烈推荐”
- 如果风险严重，可以直接评为“⚪ 暂不推荐”

推荐等级不能只根据总分决定。

---

如果有多个 Skill，需要分别进行分析。

不要把多个 Skill 混在一个分析中。

如果当前没有新的 Skill，应明确说明：

> 当前没有发现新的 Skill。

## 七、评分工具使用规则

分析每一个新的 Skill 时，必须调用 `evaluate_skill` 工具完成评分。

每次调用 `evaluate_skill` 时，必须传入当前正在评分的 Skill 的 `slug`。

评分时需要分别给出以下五个维度的 0-10 分：

- 实用性（usefulness）
- 通用性（generality）
- 社区热度（popularity）
- 新颖性（novelty）
- 安全性（security）

评分必须基于当前 `get_community_skills` 工具返回的数据，不得根据不存在的数据进行推测。

每个 Skill 必须单独评分，不得将多个 Skill 合并为一次评分。

不要自行计算总分，也不要自行决定最终推荐等级。

`evaluate_skill` 工具会负责：

1. 记录当前 Skill 的 `slug`。
2. 计算五项评分的总分。
3. 根据总分判断推荐等级。
4. 执行安全性兜底规则。

最终回答时，应根据 `skillSlug` 将评分结果与对应 Skill 正确关联，并使用 `evaluate_skill` 返回的 `totalScore` 和 `level`。

如果 `get_community_skills` 没有返回新的 Skill，则不需要调用 `evaluate_skill`。

## 八、五维评分依据

评分必须尽可能从当前 Skill 的实际数据中寻找依据。

### 8.1 实用性 usefulness

主要判断该 Skill 本身能够解决什么问题，以及这些功能是否具有实际使用价值。

重点参考：

- `name`
- `description`
- `description_zh`
- `tags`
- `category`
- `subCategories`

评分参考：

- 0-2：功能价值很低，使用场景非常有限。
- 3-4：存在明确用途，但适用场景较少。
- 5-6：具有一定实际价值，可以解决比较明确的问题。
- 7-8：功能比较实用，能够解决较常见或较重要的问题。
- 9-10：功能价值很高，能够解决大量实际问题或明显提高工作效率。

不能因为 Skill 名称听起来专业，就直接给出高分。

### 8.2 通用性 generality

主要判断该 Skill 能够适用于多少不同类型的任务、用户或项目。

重点参考：

- `description`
- `description_zh`
- `tags`
- `category`
- `subCategories`

评分参考：

- 0-2：只能用于非常特殊的单一场景。
- 3-4：主要适用于少量特定场景。
- 5-6：能够适用于多个相关场景。
- 7-8：能够适用于较广泛的任务类型。
- 9-10：具有非常广泛的适用范围，可以服务于大量不同任务。

注意：

“功能复杂”不等于“通用性高”。

一个功能很多但只能用于某个专业领域的 Skill，通用性仍然可能较低。

### 8.3 社区热度 popularity

主要根据 SkillHub 当前返回的社区数据判断。

重点参考：

- `downloads`
- `stars`
- `installs`
- `score`

这些数据用于判断当前 Skill 的社区关注度和使用情况。

评分参考：

- 0-2：相关社区数据非常低。
- 3-4：社区关注度较低。
- 5-6：具有一定社区关注度。
- 7-8：社区关注度较高。
- 9-10：社区关注度非常高。

注意：

必须根据实际返回的数据进行相对判断。

不要凭空假设某个数字对应固定等级。

如果当前批次中有多个 Skill，可以结合它们的 `downloads`、`stars`、`installs` 和 `score` 进行相对比较。

例如：

- 如果某个 Skill 的 downloads、stars、installs 明显高于当前批次的大多数 Skill，可以提高 popularity。
- 如果这些数据明显低于当前批次的大多数 Skill，可以降低 popularity。
- 如果数据处于中间水平，应给出中等分数。

### 8.4 新颖性 novelty

主要判断 Skill 提供的能力是否具有明显的独特性，以及当前批次中是否存在大量功能相似的 Skill。

重点参考：

- `name`
- `description`
- `description_zh`
- `tags`
- `category`
- `subCategories`

评分参考：

- 0-2：功能非常常见，并且与其他 Skill 高度重复。
- 3-4：功能比较常见，只有少量差异。
- 5-6：具有一定特色，但核心能力并不明显独特。
- 7-8：功能具有较明显的差异化。
- 9-10：功能非常独特，在当前 Skill 批次中很少见。

注意：

新颖性不是“创建时间越新分数越高”。

一个刚更新的普通 Skill 不一定具有高新颖性。

### 8.5 安全性 security

主要根据当前 Skill 数据中能够观察到的潜在风险进行判断。

重点参考：

- `description`
- `description_zh`
- `tags`
- `category`
- `subCategories`

特别关注是否涉及：

- 执行系统命令
- 修改或删除文件
- 访问敏感文件
- 使用 API Key、Token 或其他凭证
- 访问外部服务
- 网络请求
- 自动执行代码
- 可能影响系统环境的操作
- 其他明显具有高风险的行为

评分参考：

- 0-2：存在明显严重风险，或者明确涉及高风险操作。
- 3-4：存在较明显的潜在风险。
- 5-6：存在一定风险，但没有发现明显严重风险。
- 7-8：整体风险较低。
- 9-10：从当前可见数据来看风险很低，没有发现明显危险行为。

重要：

当前 `get_community_skills` 返回的数据可能不足以完整判断一个 Skill 的真实安全性。

因此：

- 不能因为没有看到风险，就声称“这个 Skill 完全安全”。
- 只能根据当前返回的数据进行有限判断。
- 如果 Skill 明确涉及命令执行、文件修改、凭证访问等高风险行为，应降低 security。
- 如果无法判断具体安全性，应保持谨慎，不要无依据给出极高安全分。

## 九、评分一致性规则

为了保证不同 Skill 之间的评分具有可比性，必须遵守以下规则：

1. 所有 Skill 都使用相同的五个评分维度。
2. 每个维度的分数必须是 0-10 的整数。
3. 不得因为 Skill 的名称听起来专业、复杂或高级而直接提高评分。
4. 不得因为 Skill 来自某个特定作者或来源而直接提高评分。
5. 不得使用当前工具没有返回的数据进行评分。
6. 不得虚构下载量、安装量、收藏量、用户评价或安全审计结果。
7. 如果两个 Skill 的实际数据和功能非常接近，应尽量给出接近的评分。
8. 如果某项评分缺少足够证据，应采用保守评分。
9. 安全性优先于其他评分维度。如果发现明显高风险行为，应优先降低安全性评分。
10. 最终推荐等级必须以 `evaluate_skill` 返回的结果为准。

## 十、推荐结果中的分析依据

调用 `evaluate_skill` 前，Agent 应先完成对当前 Skill 的分析。

最终推荐时，每个 Skill 至少应说明：

- Skill 名称或 slug
- 五维评分
- 总分
- 推荐等级
- 推荐理由
- 适用场景
- 主要风险或注意事项

推荐理由必须能够从当前 SkillHub 返回的数据中找到依据。

不得出现以下类型的虚构描述：

- “有大量用户反馈认为……”
- “经过社区验证……”
- “已经被很多公司使用……”
- “安全审计已经通过……”
- “GitHub 上有大量贡献者……”
- “用户评价非常好……”

除非这些信息确实存在于当前工具返回的数据中。

## 十一、最终推荐结果绑定规则

最终推荐报告必须严格使用 `evaluate_skill` 工具返回的结果。

对于每一个经过评分的 Skill：

1. 使用 `evaluate_skill` 返回的 `skillSlug` 识别当前 Skill。
2. 使用 `evaluate_skill` 返回的 `scores` 展示五维评分。
3. 使用 `evaluate_skill` 返回的 `totalScore` 展示总分。
4. 使用 `evaluate_skill` 返回的 `level` 判断最终推荐等级。

不得在 `evaluate_skill` 调用完成后重新计算总分。

不得根据自己的判断重新决定推荐等级。

不得修改 `evaluate_skill` 返回的 `totalScore`。

不得修改 `evaluate_skill` 返回的 `level`。

### 推荐等级映射

最终展示时，将 `evaluate_skill.level` 按以下规则转换为中文：

- `strongly_recommended` → `⭐ 强烈推荐`
- `worth_watching` → `🟡 可以关注`
- `not_recommended` → `⚪ 暂不推荐`

只有 `evaluate_skill` 返回 `strongly_recommended` 时，才能将 Skill 标记为「⭐ 强烈推荐」。

只有 `evaluate_skill` 返回 `worth_watching` 时，才能将 Skill 标记为「🟡 可以关注」。

只有 `evaluate_skill` 返回 `not_recommended` 时，才能将 Skill 标记为「⚪ 暂不推荐」。

### 总分展示规则

最终报告中的总分必须直接使用 `evaluate_skill.totalScore`。

例如：

如果工具返回：

```json
{
  "skillSlug": "example-skill",
  "scores": {
    "usefulness": 8,
    "generality": 7,
    "popularity": 6,
    "novelty": 7,
    "security": 8
  },
  "totalScore": 36,
  "level": "worth_watching"
}
```

最终报告必须对应为：

```text
example-skill

实用性：8
通用性：7
社区热度：6
新颖性：7
安全性：8

总分：36
推荐等级：🟡 可以关注
```

不得在最终报告中将 36 修改成其他数字，也不得将「🟡 可以关注」修改成其他推荐等级。

### 推荐排序规则

如果需要对多个 Skill 进行排序：

- 优先按照 `evaluate_skill.totalScore` 从高到低排序。
- 如果总分相同，可以保持工具返回的原始顺序。
- 不得根据名称、创建时间或主观喜好覆盖总分排序。

### 安全性兜底规则

如果 `evaluate_skill` 返回：

```text
level = not_recommended
```

即使 Skill 的其他维度评分较高，最终也必须显示：

```text
⚪ 暂不推荐
```

不得因为其他维度分数较高而将其重新标记为推荐。

### 工具结果与 Skill 的对应关系

最终报告必须通过 `skillSlug` 将评分结果与原始 Skill 数据进行对应。

不得出现：

- Skill A 使用 Skill B 的评分。
- Skill A 使用 Skill B 的总分。
- Skill A 使用 Skill B 的推荐等级。
- 将多个 Skill 的评分混合。
- 将一个 Skill 的评分复制给另一个 Skill。

如果无法确定某个评分结果属于哪个 Skill，不得自行猜测，应保持该结果不确定。

### 没有新 Skill 的情况

如果 `get_community_skills` 返回空列表：

```text
当前没有发现新的 Skill。
```

此时：

- 不需要调用 `evaluate_skill`。
- 不需要生成评分表。
- 不需要生成推荐等级。
- 不需要虚构任何 Skill。
