# Debugging Skill

## 作用

用于帮助 Agent 定位、分析和解决项目中的代码问题。

核心流程：

`理解问题 → 收集信息 → 定位代码 → 分析原因 → 修改代码 → 验证结果`

## 使用场景

当用户要求：

- 修复 Bug
- 解决报错
- 排查异常
- 定位代码问题
- 修复 TypeScript / JavaScript 错误
- 修复构建错误
- 修复测试失败
- 修复运行时问题

时使用此 Skill。

如果用户只是要求分析或解释代码，优先使用 Code Analysis Skill。

## 核心原则

1. Debugging 必须基于实际代码、错误信息和实际执行结果。
2. 不要在没有足够证据的情况下直接修改代码。
3. 不要把错误现象直接当成根本原因。
4. 不要因为代码“看起来有问题”就直接修改。
5. 无法确定原因时，应继续收集必要信息，而不是猜测。
6. 修改代码后，应尽可能进行实际验证。
7. 不要把推测当成事实。

## 执行流程

### 1. 理解问题

明确：

- 用户遇到了什么问题
- 问题发生在哪里
- 是否提供了错误信息
- 是否提供了复现步骤

如果信息不足，根据需要进一步调查。

### 2. 收集信息

根据问题选择合适的工具：

- `list_files`：不了解项目结构时使用
- `search_files`：定位相关代码、函数、变量或错误信息
- `read_file`：读取实际源码
- `run_command`：复现错误、运行构建或测试
- `write_file`：确认原因后修改代码

不要机械地使用所有工具，也不要重复执行没有必要的操作。

### 3. 复现问题

如果问题可以通过命令复现，应尽可能先复现。

例如：

`run_command("npm run build")`

通过实际错误信息确认问题是否存在。

如果当前环境无法复现，应明确告诉用户，不要声称已经解决。

### 4. 定位问题

根据错误信息和搜索结果找到相关文件。

需要多个文件才能判断时，应继续读取相关文件。

不要根据文件名、函数名或工具名称猜测代码实现。

### 5. 分析原因

分析：

- 错误在哪里产生
- 数据从哪里进入
- 数据经过了什么处理
- 哪段代码导致错误
- 为什么会产生错误

区分：

- **事实**：可以从源码、错误信息或执行结果确认
- **推测**：目前无法完全确认的判断

如果原因只是推测，应继续验证。

### 6. 制定修复方案

确定原因后再修改代码。

修复应该：

- 优先解决根本原因
- 保持现有项目结构
- 保持现有代码风格
- 尽量减少修改范围
- 不修改与问题无关的代码
- 不引入不必要的依赖

### 7. 修改代码

使用 `write_file` 修改已经确认存在问题的代码。

不要通过反复修改代码来“尝试”不同的猜测。

### 8. 验证修复

修改完成后，根据问题类型选择合适的验证方式：

- 编译错误 → 运行构建命令
- 测试错误 → 运行测试命令
- 运行时错误 → 运行相关程序或命令
- 逻辑错误 → 检查执行流程，并在必要时运行测试

验证重点：

- 原错误是否消失
- 是否出现新的错误
- 修改是否破坏其他功能

### 验证禁止事项

验证过程中：

- 不要修改 `tsconfig.json` 来隐藏 TypeScript 错误
- 不要降低 TypeScript 严格程度
- 不要关闭 lint 或测试规则
- 不要修改测试代码来制造通过结果
- 不要通过修改配置文件绕过错误

如果验证命令报错：

先分析报错原因，再决定是否需要修改其他文件。

### 9. 验证失败

如果问题仍然存在：

`重新获取错误 → 重新分析 → 修改 → 再次验证`

不要直接宣布修复成功。

如果经过合理尝试仍无法确定原因，应停止猜测并告诉用户当前无法确认。

## 修改范围

Debugging 时：

- 不修改无关文件
- 不随意重构项目
- 不删除已有功能
- 不为了通过测试而修改测试
- 不通过修改配置掩盖真正的问题
- 不引入没有必要的依赖

### 指定文件优先原则

如果用户明确指定了需要修复的文件：

- 优先只分析和修改该文件
- 不要随意扩大修改范围
- 不要因为验证命令报错就直接修改其他配置
- 如果发现其他文件可能存在问题，应先确认它是否是当前问题的直接原因
- 如果无法确认，应继续调查，而不是直接修改

例如：

用户要求修复：

`tests/debug-test.ts`

则默认只能修改：

`tests/debug-test.ts`

除非能够明确证明其他文件是导致该问题的直接原因。

## 安全原则

不要执行明显具有破坏性的命令。

不要删除无关文件。

不要修改项目之外的文件。

不要读取与当前问题无关的敏感信息。

如果操作可能造成较大影响，应先停止并确认。

## 与 Code Analysis Skill 的关系

Code Analysis：

`读取 → 理解 → 分析 → 输出`

Debugging：

`发现问题 → 复现 → 定位 → 分析 → 修改 → 验证`

如果用户要求“分析并修复”，可以先进行代码分析，再进入 Debugging 流程。

## 与 Memory 的关系

Debugging Skill 不负责维护长期 Memory。

一次性的 Bug、报错、工具执行结果和调试过程通常不保存。

只有发现项目长期规范、架构决策或用户长期开发偏好时，才可以交给 Memory Agent 判断是否保存。

## 最终输出

完成 Debugging 后，应说明：

1. 问题是什么
2. 原因是什么
3. 修改了什么
4. 如何验证
5. 验证结果

如果没有完全解决，应明确说明剩余问题。

## 最终原则

**先确认问题，再修改代码；修改之后必须尽可能验证。**

任何无法从实际代码、错误信息或执行结果确认的内容，都不能直接当成事实。
