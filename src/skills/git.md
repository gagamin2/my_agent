# Git Skill

## 作用

用于帮助 Agent 理解和管理项目的 Git 状态，
包括查看仓库状态、查看修改、查看提交历史、分析分支以及执行安全的 Git 操作。

Git 操作可能影响项目历史或工作区，
因此必须根据操作风险决定是否可以直接执行。

## 使用场景

当用户要求：

- 查看 Git 状态
- 查看代码修改
- 查看 Git diff
- 查看提交历史
- 查看当前分支
- 分析 Git 问题
- 提交代码
- 创建 Git commit
- 查看某次提交
- 了解项目 Git 状态

时使用此 Skill。

如果用户要求修改代码后提交：

可以先完成代码修改和验证，
再进入 Git 流程。

## 核心原则

1. Git 操作必须基于实际仓库状态。
2. 不要根据猜测判断 Git 状态。
3. 查看状态前优先使用 `git status`。
4. 查看具体修改时使用 `git diff`。
5. 查看历史时使用 `git log`。
6. 提交前必须确认实际修改内容。
7. 不要提交没有确认过的文件。
8. 不要把构建产物、临时文件或无关文件加入提交。
9. 不要为了让 Git 状态“看起来干净”而删除用户文件。
10. 不要擅自修改 Git 历史。
11. 不要擅自执行可能丢失代码的操作。
12. 不要擅自推送到远程仓库。

## Git 操作分类

### 低风险只读操作

以下操作主要用于获取信息：

- `git status`
- `git diff`
- `git diff --cached`
- `git log`
- `git branch`
- `git remote -v`

这些操作通常可以直接执行。

### 中风险操作

以下操作会改变本地 Git 状态：

- `git add`
- `git commit`
- `git branch <name>`
- `git merge`

如果用户已经明确要求执行这些操作，
可以按照用户要求执行。

如果用户只是要求查看或分析，
不要自行执行这些操作。

### 高风险操作

以下操作可能导致代码丢失、历史改变或远程仓库改变：

- `git reset --hard`
- `git clean`
- `git checkout -- <file>`
- `git restore <file>`
- `git rebase`
- `git push --force`
- 删除分支
- 修改远程仓库

除非用户明确要求，
不要执行这些操作。

如果操作可能导致用户未提交的修改丢失，
必须先提醒用户。

## 执行流程

### 1. 理解 Git 任务

首先判断用户要求的是：

- 查看状态
- 查看修改
- 查看历史
- 分析问题
- 创建提交
- 修改 Git 历史
- 推送远程仓库

不同任务使用不同的 Git 操作。

### 2. 获取实际状态

如果不了解当前仓库状态：

使用：

`git status`

不要根据之前的状态进行猜测。

### 3. 查看具体修改

如果用户要求了解修改内容：

使用：

`git diff`

如果需要查看已经暂存的修改：

使用：

`git diff --cached`

### 4. 查看历史

如果用户要求查看提交历史：

使用：

`git log`

可以根据需要限制输出数量。

例如：

`git log --oneline -10`

### 5. 提交前检查

如果用户要求提交：

首先检查：

`git status`

然后根据需要查看：

`git diff`

确认：

- 修改了哪些文件
- 修改内容是什么
- 是否存在无关文件
- 是否存在临时文件
- 是否存在构建产物

不要在没有检查修改内容的情况下直接提交。

### 6. 创建提交

如果用户明确要求提交：

可以执行：

`git add <confirmed files>`

然后：

`git commit -m "<message>"`

提交文件必须来自已经确认的修改。

不要使用：

`git add .`

来盲目提交整个工作区。

### 7. 提交后验证

提交完成后：

使用：

`git status`

确认提交结果。

如果需要：

使用：

`git log --oneline -1`

确认最新提交。

### 8. 推送远程仓库

默认不要主动执行 `git push`。

只有用户明确要求推送时才执行。

如果用户要求推送：

先确认当前分支和远程仓库信息。

不要擅自使用：

`git push --force`

## 文件选择原则

提交时：

优先提交：

- 用户明确要求提交的文件
- 与当前任务直接相关的代码
- 已经验证过的修改

不要提交：

- `.js`
- `.map`
- `.d.ts`

等明显由构建生成的文件，
除非项目明确要求提交这些文件。

不要提交：

- 临时测试文件
- 调试日志
- IDE 配置
- 无关修改
- 密钥
- `.env`
- API Key

## 修改范围

Git Skill 默认不修改源代码。

如果用户要求：

“查看状态”

只能查看。

如果用户要求：

“查看 diff”

只能查看。

如果用户要求：

“提交这些修改”

才进入提交流程。

不要因为发现工作区存在其他修改，
就自行修改或删除这些修改。

## 高风险操作确认流程

当用户要求执行可能导致代码丢失、提交历史改变或远程仓库改变的操作时，
不能直接执行命令。

必须按照以下流程：

### 第一步：识别风险

判断操作是否可能：

- 删除文件
- 丢弃未提交修改
- 修改已有提交历史
- 覆盖远程历史
- 删除分支
- 修改远程仓库

如果存在风险，则进入确认流程。

### 第二步：检查当前状态

先使用只读 Git 命令确认当前状态。

例如：

`git status --short`

必要时使用：

`git diff`

确认实际会受到影响的文件。

### 第三步：向用户说明风险

明确告诉用户：

- 哪些文件可能受到影响
- 哪些修改可能丢失
- 执行的 Git 操作是什么

不要只说“这个操作有风险”。

### 第四步：等待明确确认

必须等待用户明确确认后才能执行危险操作。

例如用户明确回复：

- “确认”
- “确定”
- “继续”
- “执行”

才可以继续。

如果用户没有明确确认：

不要执行危险命令。

### 第五步：执行操作

用户明确确认后，
才执行对应的 Git 命令。

### 第六步：验证结果

执行完成后：

- 查看 Git 状态
- 根据操作需要检查结果
- 向用户说明最终状态

## 特别禁止

以下命令不能因为用户使用了“清理”“恢复”“重置”等模糊表达就直接执行：

`git reset --hard`

`git clean`

`git restore`

`git checkout --`

`git rebase`

`git push --force`

如果用户没有明确说明要执行具体危险操作，
应先询问并确认。

## 安全原则

### 不要丢失用户修改

执行可能覆盖或删除文件的操作之前：

先确认用户是否希望丢弃这些修改。

不要擅自执行：

`git reset --hard`

`git clean`

`git restore`

来“清理项目”。

### 不要修改远程历史

不要擅自执行：

`git push --force`

不要擅自修改已经存在的提交历史。

### 不要提交敏感信息

如果发现：

- API Key
- 密码
- Token
- `.env`

等敏感信息：

不要加入提交。

应提醒用户。

## Git Commit 规范

提交信息应该：

- 简洁
- 准确
- 描述实际修改
- 不夸大修改内容

例如：

`新增 Testing Skill 并完善测试流程`

不要写：

`修复所有问题并完成全部功能`

除非实际确实完成了这些内容。

## 最终输出

完成 Git 操作后，应说明：

1. 执行了什么 Git 操作
2. 涉及哪些文件
3. 提交信息是什么
4. 操作结果
5. 如果没有执行操作，说明原因

例如：

提交完成。

提交信息：

`新增 Testing Skill 并完善测试流程`

涉及文件：

- `src/agent/agent.ts`
- `src/skills/testing.md`

提交成功。

## 最终原则

**Git 操作必须基于实际仓库状态。**

**提交前确认修改，提交时只提交确认过的文件。**

**涉及代码丢失、历史修改或远程仓库的操作必须谨慎处理。**
